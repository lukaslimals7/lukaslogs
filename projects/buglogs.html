01 / What it is

What was reported, where, and what it paid.

Bug-bounty write-ups are scattered across HackerOne, and the good ones are buried under thousands of duplicates. buglogs takes the public report list and turns it into something you can actually query: title, program, weakness, bounty, votes and link, all full-text searchable, all exportable to plain markdown.

It is not a clone of anyone's site. It is a personal research tool that happens to be public — the kind of thing you build when you keep opening the same five reports and wishing you could just search them.

02 / The classes

Eighteen buckets, from the HackerOne weakness names.

Every report is filed under one of eighteen classes, derived from the HackerOne weakness name. When a program filed the report without one, the class is guessed from the title — so nothing ends up in a drawer marked "miscellaneous".

The long tail is the point. Memory corruption and business logic are rare and expensive; information disclosure is everywhere and mostly unpaid. That shape is the whole argument for keeping this data locally — you start seeing what a program actually cares about.

03 / How it is built

Python standard library. Nothing else.

No framework, no pip, no build step. sqlite3 with FTS5 for search, urllib for the one HTTP fetch, http.server for the page. If Python runs, this runs.

buglogs/
├── kb/
│   ├── db.py       ← schema + connection (SQLite + FTS5)
│   ├── classify.py ← HackerOne weakness names → 18 classes
│   ├── ingest.py   ← the public CSV → data/kb.db
│   ├── wiki.py     ← data/kb.db → markdown (llm-wiki layout)
│   ├── server.py   ← the search page, on localhost
│   └── crawl.py    ← optional public write-ups, off by default
├── public/index.html
├── tests/test_kb.py
├── LICENSE         ← MIT, code only
└── DATA_PROVENANCE.md

The pipeline is four steps, and each one is idempotent: fetch the list, fetch the write-ups (optional), derive the classes and aggregates, export the markdown. Re-run any of them; nothing is lost.

04 / The markdown half

Readable by you and by your agents.

The same data is exported as an llm-wiki: one page per report under raw/reports/, one page per class under concepts/, one per program under entities/, with index.md, SCHEMA.md and a log.md. Wikilinks cross-reference everything, so it opens in Obsidian as a graph rather than a folder.

Fifteen thousand pages of it. That is the part your agents actually read.

wiki/
├── index.md  SCHEMA.md  log.md
├── raw/reports/     15,219 pages, one per report
├── concepts/        18 pages, one per weakness class
└── entities/        428 pages, one per program

05 / The honest limits

What it does not do.

A fresh clone has no report bodies. The metadata is complete; the write-ups are not. Fetching them means contacting hackerone.com, politely and slowly, so it is a separate command you run only if you want it — python3 -m kb.crawl, resumable, one request a second, and it stops the moment HackerOne says stop.

And the data is a snapshot of a community dataset, not a live feed. Re-run the ingest to refresh it. Report titles and write-ups belong to their authors and to the programs that disclosed them — the code is MIT, the data is credited, not licensed.

06 / Run it

Three commands.

Python 3.11 or newer. That is the whole requirement — FTS5 ships with sqlite3.

git clone https://github.com/lukaslimals7/buglogs.git
cd buglogs

python3 -m kb.ingest     # fetch the CSV, build data/kb.db
python3 -m kb.wiki       # build the markdown wiki under wiki/
python3 -m kb.server     # search page on http://127.0.0.1:8765
